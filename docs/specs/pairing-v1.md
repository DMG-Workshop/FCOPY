# Nearby pairing protocol, v1

**Status:** Draft for external review
**Phase:** 2 (Nearby quick drop)
**Owner:** FCOPY core
**Implementation status:** Not implemented. This document defines the target.
**Related:** `crates/fc-remote/src/tls.rs`, `crates/fc-remote/src/crypto.rs`,
`crates/fc-remote/src/protocol.rs`

## 1. Purpose and scope

This protocol lets two FCOPY devices on the same network establish a trusted
relationship without a pre-shared password. A person on the sending device types a
short PIN that the receiving device shows on screen. The result is a pinned TLS
identity for the other device.

In scope:

- Pairing a sender (S) and a receiver (R) over QUIC (`ALPN fcopy/1`).
- A time-limited receive window and a one-time PIN.
- Pinning the peer's certificate fingerprint on both sides after success.

Out of scope:

- Compatibility with any other product's wire protocol. This protocol is independent.
- Per-transfer consent. That is covered by the transfer offer, not pairing (section 9).
- Browser and mobile-browser pairing. Browsers cannot read the TLS exporter, so they
  need a separate, weaker design. It is not part of v1.
- Group pairing or relays through a cloud service.

## 2. Terms

| Term | Meaning |
|---|---|
| Sender S | The device that initiates pairing. Its user types the PIN. |
| Receiver R | The device whose receive window is open. It shows the PIN. |
| Fingerprint | `SHA256:` followed by unpadded base64 of SHA-256 over the certificate DER (section 4). |
| Exporter | `export_keying_material` value from the TLS session, label `EXPORTER-fcopy-pairing-v1`, 32 bytes, empty context. |
| PIN | Six decimal digits, uniformly random, generated by R. |
| Window | The period during which R accepts pairing. Default 10 minutes. |

## 3. Preconditions

1. QUIC with TLS 1.3, ALPN `fcopy/1`. Both sides use self-signed identities from
   `Identity`.
2. The protocol runs on a dedicated bidirectional stream, separate from transfer streams.
3. Pairing is refused on any connection that is not from the receive window's
   allowlist (section 8).

## 4. Identity fingerprint

**Current implementation:** `fingerprint(cert_der)` = `"SHA256:" ‖ base64(SHA-256(cert DER))`.

**Open question (review item Q1):** the fingerprint covers the whole certificate. A
routine certificate renewal would therefore change the fingerprint and break every
pin. The proposed alternative hashes only the SubjectPublicKeyInfo. Switching would
require a migration for existing pins, so this spec uses the current definition
and flags the change for decision.

## 5. Receive window and PIN

R enters the window only on user action. While the window is open:

- R advertises `_fcopy._udp.local.` with TXT `fp`, `ver=1`, and a generic `name`.
  Default name: `FCOPY-` plus four hex digits. The hostname is not used by default.
- R generates a PIN from the operating system's CSPRNG. Digits are drawn by rejection
  sampling so every value from `000000` to `999999` is equally likely.
- The PIN is valid for 60 seconds. After that R generates a new one. The UI shows the
  remaining time.
- The window closes on: user cancel, timeout (default 10 min), three failed PIN
  attempts, or a successful pairing.
- Only one window is open at a time per device.

The PIN is never sent in a URL, query string, header, or log line. It is shown only on
R's screen.

## 6. Cryptographic construction

### 6.1 Password-authenticated key exchange

The exchange uses SPAKE2 (RFC 9382). **Review item Q2:** pick the RFC 9382 ciphersuite
(Ed25519 with SHA-256 is proposed) and confirm the exact suite name against the RFC
and the chosen crate before implementation.

The password input to SPAKE2 is derived as:

```
w = Argon2id(password = PIN as ASCII digits,
             salt     = "fcopy-pair-v1" ‖ fingerprint_R bytes,
             m = 19456 KiB, t = 2, p = 1,
             output   = 64 bytes)
```

The parameters are the OWASP minimum for Argon2id. Binding the salt to `fingerprint_R`
means a PIN precomputed against one device cannot be reused against another.
**Review item Q3:** confirm the parameters on the lowest-end target device.

Identities in SPAKE2:

- `idS = "S:" ‖ fingerprint_S`
- `idR = "R:" ‖ fingerprint_R`

### 6.2 Transcript and key confirmation

Let `TT` be the length-prefixed concatenation of:

```
"fcopy-pair-v1" | ALPN | versions | exporter | fingerprint_S | fingerprint_R | pA | pB
```

`versions` is the byte list from `PairRequest`, so a version list altered in transit
changes `TT` and fails the MAC check.

Here `pA` and `pB` are the SPAKE2 messages. Each field is prefixed with its length as
a `u32` big-endian.

From the SPAKE2 shared secret `K`:

```
keys    = HKDF-SHA256(salt = exporter, ikm = K, info = "fcopy-pair-v1 confirm", len = 64)
K_conf_S = keys[0..32]
K_conf_R = keys[32..64]
mac_S   = HMAC-SHA256(K_conf_S, SHA-256(TT))
mac_R   = HMAC-SHA256(K_conf_R, SHA-256(TT))
```

Both MACs are compared in constant time.

## 7. Message flow

Messages are postcard-encoded and length-prefixed, as in `protocol.rs`. The new
variants are appended to `Message`. The protocol version stays at 1, so an old peer
refuses them cleanly.

```
S                                                    R
│                                                    │  window open, PIN shown
│  (user types PIN; S knows fingerprint_R via TLS)   │
│── PairRequest{v, fp_S, name_S, pA} ───────────────▶│  checks window, rate limits, size
│                                                    │  w = Argon2id(PIN, salt)
│                                                    │  pB, K_R
│◀─ PairResponse{fp_R, pB} ──────────────────────────│
│  K_S, derive keys, mac_S                           │
│── PairConfirm{mac_S} ─────────────────────────────▶│  verify mac_S (constant time)
│                                                    │  on fail: attempts += 1, reply PairFailed
│◀─ PairConfirmed{mac_R} ────────────────────────────│  on success: close window, pin S
│  verify mac_R, pin R                               │
```

Rules:

- R counts an attempt on each `PairConfirm` that fails. A `PairRequest` that never
  reaches `PairConfirm` gives an attacker no guess, so it is rate limited, not
  counted as a guess.
- After three failed attempts, R closes the window and invalidates the PIN.
- On success, R invalidates the PIN immediately, so it cannot be reused.
- Any failure produces the same `PairFailed` reply. The reply does not say whether the
  PIN was wrong, expired, or the window was closed. It also does not reveal the
  attempt count to the sender. The receiver's own screen shows "attempts left".
- `PairRequest` carries a protocol version list. If there is no common version, R
  replies `VersionMismatch`. This is the only error that reveals a reason.

### 7.1 Messages

```
PairRequest  { versions: Vec<u8>, fp_s: String, name_s: String, pake_a: Vec<u8> }
PairResponse { fp_r: String, pake_b: Vec<u8> }
PairConfirm  { mac_s: [u8; 32] }
PairConfirmed{ mac_r: [u8; 32] }
PairFailed   { code: PairErrorCode }   // Generic | Busy | VersionMismatch | WindowClosed
```

`PairErrorCode::Generic` is used for every wrong-PIN, expired-PIN, and closed-window
case. `Busy` means another pairing is in progress. `WindowClosed` is returned only
when the window is closed entirely, since that state is already visible through
mDNS.

## 8. Limits

| Limit | Value |
|---|---|
| Window lifetime | 10 min default, user configurable up to 30 min |
| PIN lifetime | 60 s |
| Failed PIN attempts per window | 3 |
| Concurrent pairings | 1 per device |
| `PairRequest` size | 4 KiB |
| Display name | ≤ 64 UTF-8 bytes |
| Pairing requests per source IP | 1 per 2 s, burst 3 |
| Total pairing time | 30 s, then the stream is reset |

Display-name rules: trim whitespace, reject control characters, and reject
bidirectional override characters (U+202A–U+202E, U+2066–U+2069). A name that fails
these rules is replaced with the fingerprint's first eight characters. The UI treats
the name as untrusted text and escapes it.

Success probability for an online attacker in one window is at most 3 / 10⁶ = 3·10⁻⁶.

## 9. After pairing

On success both sides store a pin record:

```
PinRecord { fingerprint, display_name, first_paired, last_seen }
```

- The pin is keyed by fingerprint, not by IP address, because LAN addresses change.
  **Review item Q4:** this differs from the current profile pins, which are bound to
  an endpoint. Keying by fingerprint means a device that moves IP addresses stays
  paired, but it also means the pin must not be trusted for a different host.
- Later connections use the existing `PinnedVerifier`. A matching fingerprint is
  required, and a changed fingerprint hard-fails and requires re-pairing.
- Pairing does not grant transfer consent. Each transfer offer is still subject to
  the receiver's policy: prompt by default, or auto-accept if the user chose
  "always accept" for that device.
- Either side can remove the pin. Removal does not notify the peer.

## 10. Threat analysis

| Threat | Mitigation |
|---|---|
| Passive eavesdropper | TLS 1.3 on QUIC. The PIN is never on the wire in clear. |
| Active man in the middle relaying the handshake | The exporter differs in each TLS session, and it is in the transcript. A relay gives the attacker only one PIN guess per attempt. |
| Offline PIN guessing from a captured transcript | SPAKE2 does not let a passive observer test guesses. Argon2id slows precomputation. |
| Online PIN guessing | Three attempts per window, a 60-second PIN, and a 3·10⁻⁶ success bound. |
| Discovery spoofing (a fake device named like a real one) | Names are not trusted. Only a completed PAKE establishes identity. The UI shows the fingerprint's first eight characters beside the name. |
| Shoulder surfing | The PIN is visible only on R's screen, only during the window. |
| Replay | Fresh SPAKE2 scalars and a fresh exporter on every connection. |
| Denial of service | Rate limit, one concurrent pairing, 4 KiB request cap, 30 s timeout. |
| Downgrade | The version list is part of `TT` (section 6.2), so an altered list fails the MAC check. v1 defines one suite, so there is nothing weaker to downgrade to. |
| Key compromise or certificate rotation | Pin mismatch hard-fails and requires re-pairing. Q1 decides whether SPKI pinning reduces this. |
| Privacy in the open window | Generic default name, no hostname, window only on user action. |

## 11. Test requirements

Unit tests:

- PIN generation: 10,000 draws show no digit bias beyond a chi-square threshold, and
  rejection sampling is exercised at the boundary.
- Window state machine: open, expiry, three failures, success, cancel.
- Limit enforcement: rate limit, size cap, timeout.
- Transcript encoding: fixed test vectors, length-prefix correctness.
- MAC comparison is constant time.
- Display-name sanitization, including bidirectional overrides.

Integration tests over loopback QUIC:

- Correct PIN pairs, and both sides pin each other.
- Wrong PIN fails with `PairFailed`, and the third wrong PIN closes the window.
- A man-in-the-middle proxy that terminates two TLS sessions fails the PAKE.
- A replayed `PairConfirm` from an earlier session fails.
- Version mismatch returns `VersionMismatch`.
- A pin change on a later connection hard-fails.

Interoperability: none. The protocol is defined by this document.
